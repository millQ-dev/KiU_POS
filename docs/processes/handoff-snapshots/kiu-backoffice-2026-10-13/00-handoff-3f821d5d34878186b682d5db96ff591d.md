# 00 — KiU Backoffice | Handoff для разработки — индекс и рамки

**Статус:** Product Owner accepted at 13.10.2026 for product behavior. Это спецификация к проектированию, НЕ команда немедленно реализовать всё и НЕ утверждение о готовом runtime. Процесс: Level C ADR/design/security/legal gates → API contracts/UX → вертикальные PR → independent review → PO acceptance. Не выполнять blind merges.

**Пять рабочих видов:** Owner, Manager, Accountant (internal + Managed professional mode), Chef, Bar Manager. Обычный повар/бармен не получает Backoffice: Kitchen/Bar KDS + KiU Mobile. Один GlobalAccount может иметь несколько ролей по отдельным scoped grants.

**Смежные приложения:** KiU Office (web), POS/KDS, KiU Mobile (staff), клиентские guest-каналы. Q Card/Q Place — ОТДЕЛЬНЫЙ discovery, не часть текущего delivery scope.

## Подтверждённая карта продукта

1. Владелец: обзор, заведение/onboarding, продажи, финансы, склад, персонал, задачи/коммуникации, approvals/settings.
2. Менеджер: живой диспетчерский центр, 4 приоритета, задачи из контекста, смены, расписания, замены, зал/брони, касса, сервис, акции, контроль качества.
3. Бухгалтер: задачи/сроки без графиков, первичка с KiU Mobile scanner, расчёты с поставщиками, банки/сверки, налоги/e-invoice, Managed AI-assisted accounting.
4. Шеф: кухня в целом, рецепты, производство, потери, прогнозные рекомендации, закупки/приёмка/инвентаризация, люди/обучение, качество/оборудование.
5. Бар-менеджер: та же архитектура Chef, но барный объём строго в мл, кеги, открытые позиции, комплименты, барные склады и станции.

## Обязательные сквозные принципы

- **Выбор заведения при каждом входе Owner** даже если одна точка; внешний Accountant может начинать из multi-client hub. Scope Tenant/LegalEntity/Outlet/Warehouse/Station, серверная проверка на каждую mutation.
- **Права по способностям (grants)**, а не «роль автоматически умеет всё»: отдельные grants для приёмки, posting инвентаризации, расходных операций, брони, отправки денег, approvals и т. д. Владелец может быть одновременно бухгалтером, но Owner роль сама по себе не подменяет Accounting grants.
- **История финансов, заказов, движения склада и согласований неизменяема**: только корректирующие события, аудит и идемпотентные команды, без silently overwriting.
- **ИИ** может анализировать и готовить черновики по разрешению, не публикует рецептуры, не подписывает налоговые документы и не списывает деньги без отдельного законного подтверждения.
- **Задача менеджера — его операционный контур**. Red/Orange/Yellow/White события адресуются менеджеру, не владельцу автоматически. Менеджер сам вручную эскалирует владельцу. Отдельные ранее принятые владельческие approval requests (например, техкарты, превышение платёжного лимита) и уведомления о технологических отклонениях требуют самостоятельного workflow; не смешивать эти категории при проектировании routing.
- **Безопасность продуктов питания** нельзя обойти объяснением при технологическом отклонении.
