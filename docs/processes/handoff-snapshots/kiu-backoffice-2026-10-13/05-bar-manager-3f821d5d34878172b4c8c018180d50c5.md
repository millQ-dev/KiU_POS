# 05 — Bar Manager | мл, кеги, открытые позиции, комплименты

**Статус: PO ACCEPTED.** Пятый кабинет, технологически переиспользует Chef components/workflows: recipes/version approval by Owner, production, inventory permissions, purchase routes, QA/checklists, staff mobile learning, maintenance, AI, handoff, stock posting. Не повторять UI/бизнес-логику там, где нет барного отличия.

## Специфика склада и ревизий

- **Единица учёта объёма напитков — миллилитр (мл)**. Не вводить ¼ бутылки, проценты заполнения, «полбутылки» и другие приблизительные UI единицы как количественный факт.
- **Один агрегированный остаток по SKU и location**, а НЕ tracking каждой открытой бутылки. Закрытые бутылки конвертируются в общий миллилитровый объём; при ревизии открытого содержимого измеряют мл мерником, заносят факт. Не требовать pouring из бутылки в мерник как единственно допустимую физическую процедуру, если это нарушает санитарные правила конкретного продукта; точность измерения декларируется.
- Учёт открытых бутылок в ценностном смысле есть, но не отдельная сущность учётного stock unit.
- **Кеги/разливное пиво/напитки**: ёмкость в мл, подключение/замена, продажи по мл, технологические потери (пена, промывка, подключение, остатки); нормативы на тип напитка/оборудование. Если отклонение — причина/аудит/уведомление по согласованному chef-like workflow, без остановки производства.
- **Барные станции**: заведение выбирает общий warehouse pool или раздельные balances по station с audited transfers. Физический склад с кухней может быть общим, но consumption attribution к kitchen/bar остаётся честной.

## Управление напитками и ценами

- Bar Manager сам настраивает modifier policy совместно с владельцем: доп. порция/замена алкоголя либо отдельная меню-позиция (шот по прайсу), либо **открытая позиция** с порционным расходом/стоимостью. Фактические ингредиенты и расход всегда фиксируются в мл.
- **Открытая позиция возможна только если Owner включил соответствующее разрешение для заведения.** Бармен в Bar POS составляет коктейль из конкретных ингредиентов с точными количествами в мл, вводит цену. POS вычисляет **жёсткий минимальный порог цены** на базе пропорциональной стоимости стандартных порций/шотов из действующего утверждённого прайса, суммируя ингредиенты по согласованному правилу. Цена НИЖЕ ПОЛА блокируется сервером. Даже Owner/Manager/VIP на уровне отдельного заказа не могут обойти абсолютный floor; изменение глобальной price policy — отдельное authorized configuration действие, audited/versioned, не оперативная скидка.
- Открытый коктейль = потенциально рискованная операция: событие всегда фиксируется с временем, барменом, POS station, ingredients/ml, price, receipt/order/revisions; **не пушить Owner каждый раз**, только suspicious patterns/exception report.
- **Комплименты — отдельная операция нулевой цены**, а не обход floor продажи. Бармен сам оформляет комплименты; **лимит задаёт Bar Manager**, по бармену/смене ИЛИ на бар/период, либо в комбинации — способ выбирает заведение. После исчерпания лимита — no self-approval; внеплановые проливы/бой не смешивать с комплиментами.
- Пролив/бой/ошибка/комплимент фиксируются барменом в POS с причиной, SKU/мл, actor, station, системой записанным временем и опциональным фактическим временем события. Эти операции risk-audited. **Видеонаблюдение сейчас НЕ интегрируем**; хранить точную временную отметку для ручного поиска CCTV, будущем deep-link интеграция возможна.
- Акции и Happy Hours может создавать **Manager, Owner, Bar Manager**, если выданы права. **Автоматические скидки по расписанию — BASE POS functionality**; общая Sales promotions engine, без отдельного барного implementation fork. Floor для открытых позиций не отменяется акциями.
- **KDS / Bar POS routing — BASE**: заказ официанта автоматически route по станциям, кухня получает кухню, бар — напитки; официант получает per-line statuses. Не считать отдельным premium feature или барной новацией.

## Права и AI

- Bar Manager самостоятельно управляет **ручным стоп-листом напитков**; система по stock shortage только предлагает Manager заблокировать. Владелец может делегировать grants, но назначенный Bar Manager не просит approve на каждое изменение.
- Барные официальные техкарты публикуются только после Owner approval; **барные заготовки** (сироп, настойка, кордиал, премикс) подтверждает Bar Manager самостоятельно в пределах опубликованных techcards; отклонения по chef rule.
- Общая staff library, QA, maintenance, AI и expense/purchase rights совпадают с Chef с учётом product scope.

## Acceptance

1. Общий SKU джина хранится как sum ml across sealed/open inventory; нет entity «бутылка №1» для отдельного учёта.
2. POS не продаёт open cocktail ниже computed min независимо от роли, скидок, «VIP» и ручной правки цены.
3. Comp с нулевой оплатой проходит как отдельная audited allowance operation в пределах Bar Manager limit, не как скрытая discount.
4. Кег: при смене и технологическом расходе пересчёт остатков в мл и причина; no fabricated precision.
5. Frontend и backend enforcement одинаковы: роль Manager без permission не может повысить/понизить floor в конкретном чеке.
6. Bar/Kitchen stock общего физического места не удваивается.
