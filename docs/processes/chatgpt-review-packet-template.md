# Шаблон: пакет ревью для ChatGPT

Используется перед merge. Cursor-агент заполняет пакет и **выделяет его отдельным блоком** в конце ответа. Product Owner копирует пакет в стратегический ChatGPT-чат.

## Правила безопасности (обязательно)

В пакет **нельзя** включать:

- секреты, токены, пароли, ключи API
- содержимое `.env`, connection string с реальными credentials
- персональные данные сотрудников/клиентов
- полную историю чата Cursor
- сырые дампы БД, логи с PII
- внутренние инструкции системы, которые не относятся к продукту

В пакет **можно** включать:

- цель блока и acceptance criteria
- ветку, commits, ссылку на PR/Issue (публичные)
- краткое «что изменилось» человеческим языком
- список ADR / решений (Accepted / Proposed / не решалось)
- результаты тестов без секретов
- риски, открытые вопросы Product Owner
- рекомендацию: merge / не merge / merge после правок

Язык пакета: **русский**, простой. Технические термины — сразу пояснять в скобках.

---

## Формат пакета (копировать отсюда)

```text
=== ПАКЕТ ДЛЯ CHATGPT (безопасный handoff) ===
Проект: MillQ
Роль получателя: стратегический / технический ревьюер Product Owner (не Origin APPROVE)
Задача: оценить блок для PO и сказать: approve / правки / блокеры (совет PO; не формальный Origin merge gate)

1) Цель блока
- ...

2) Ссылки
- Branch: ...
- Tip commit: ...
- Base: main @ ...
- PR: ... (или «ещё не создан»)
- Issue: ... (или «нет»)
- Checkpoint doc: docs/processes/current-state.md

3) Контекст продукта (кратко)
- ...

4) Что сделано в этом блоке
- ...

5) Что сознательно НЕ сделано
- ...

6) Решения
- Accepted (не менялись / подтверждены): ...
- Proposed (нужно решение PO): ...
- Scaffolding (временно, не ADR): ...

7) Проверки
- Тесты: ...
- Build/typecheck: ...
- Что не проверялось: ...

8) Риски и вопросы к Product Owner
- ...

9) Рекомендация агента-исполнителя
- ...

10) Просьба к ChatGPT-ревьюеру
Важно: твой вердикт — совет Product Owner. Это не формальный Origin APPROVE и не замена Depot CI / Bugbot (Level B).
Ответь структурировано:
A. Вердикт для PO: APPROVE / APPROVE WITH CHANGES / BLOCK
B. Почему (2–5 пунктов)
C. Обязательные правки до merge (если есть)
D. Можно ли мерджить архитектурные docs отдельно от кода (если уместно)
E. Что должно войти в следующее ТЗ / следующий блок
=== КОНЕЦ ПАКЕТА ===
```
