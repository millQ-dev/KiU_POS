## Implemented screens and client architecture

[App.tsx][app] actually mounts Company Identification → PIN → Opening Cash → CashierShell, with Closing Cash and a public guest menu at `/m/:token`. Production cashier entry is mounted, not merely the older README's ready stub. The development bootstrap is explicitly separate. There are no implemented Office launcher, KDS application, Floor/Table runtime, guest-feedback flow, or discount control in the audited web source.

Inside CashierShell: page navigation, Quick Access, product grid, basket, quantity editor, modifier modal, allergy panel, commercial status and checkout. Checkout contains cash receipt, fiscal state and completion feedback. This confirms source integration, not a browser run against a real restaurant database.

There is **not yet one shared typed HTTP contract layer**:

- [posApi][client] has generic `request<T>`, cookie credentials and `ApiError`, but casts JSON to local TS types.
- [sessionClient][session] supplies `sessionFetch`; screens still parse authentication, cash and checkout JSON themselves.
- [allergenApi][allergen-client] duplicates transport/error parsing; non-JSON error responses throw JSON parse errors.
- [web types][types] are handwritten; backend Zod inputs live inside API modules. [packages/contracts][contracts] exports operational facts/intelligence contracts, not these POS HTTP DTOs. Web does not depend on that package.
- No second tax, modifier line-gross, discount or allergen decision engine was found in web. Change preview and input validation exist; accepted money and gate state come from the server. Do not move backend calculations into web to fill missing endpoints.

## Defects versus absent capabilities

### UI wiring candidates against already merged routes

1. **Uncertain add-item response:** [CashierShell][shell] `onSelectSlot` / `onConfirmWeighted` leave an old basket after response loss. The server may already have appended/incremented a line. Reconcile using GET before another mutation; never silently repeat a non-idempotent select.
2. **Session transport failure:** [sessionClient][session] + App conflate HTTP failure with unauthenticated and leave network rejection unhandled. A distinct error/retry state can reuse the current GET session contract.
3. **Modifier reopen:** [shell][shell] prompts only after selection; [modal][modal] cannot be opened from the selected line editor. Cancellation of required config leaves acceptance blocked; editing a configured line has no UI path. Readback of selected option IDs/guest note is also absent from basket summary, so a correct prefilled editor needs owner coordination.
4. **Typed transport drift:** actual checkout bypasses several `posApi` methods. `posApi.advanceCheckout` declares a flattened completion whereas actual UI handles `completion.order`; no shared runtime response validation. Consolidation should be incremental, not a new BFF.
5. **Failed read versus absence:** `reloadSettlement` catches all errors and sets null. Server remains authoritative and rejects locked edits, but UI can falsely appear editable.

### Backend-owned deltas — do not repair in web

- **Effective Recipe:** main completion resolves base consumption (`OrdersService.completeOrder`); no modifier REMOVE/REPLACE/ADD application. #139 stays open. Allergy interpretation already reads effective deltas; that does not prove inventory consumption matches it.
- **Modifier freeze:** [modifiers service][modifiers] checks `frozen_at`, but audited Orders/Modifiers code does not write that column during commercial acceptance. Accepted price fingerprint validation in #138 is present; the complete M4/T8 freeze/conflict workflow is not. Confirm with the modifier owner before exposing configuration editing after acceptance.
- **Required defaults:** both modal and service suppress defaults when `required=true`; ADR-0052 says a valid selected default satisfies required unless askEveryTime. Do not fix one side independently.
- **Grants:** ADR-0052 requires `orders.line_configure` with `pos.operate`; actual configure route calls only P and ModifiersService has no principal/grant parameter. Catalog group GET checks outlet-null permission, which also deserves a scoped-grant test. This is backend auth work.
- **Kitchen text:** service appends `GUEST_NOTE_NON_AUTHORITATIVE:…` into the same string array as instructions; accepted typed logical separation is outstanding.
- **Discount authorization:** `apply()` rejects missing approvalRequestId before direct-grant handling. Accepted ADR-0051 allows direct authorized Manager/Owner grant; current implementation imposes approval universally.
- **Discount rounding:** [domain][discount-domain] uses integer division (floor), not accepted `MERCHANT_DISCOUNT_PERCENT_TO_MINOR` HALF_UP/versioned context. Reproduced: 15% of 12345 returns 1851; HALF_UP of 1851.75 is 1852. Existing test explicitly expects floor. Passing current tests does not establish conformance to the revised ADR.

Full KDS delivery/ack authority, customer invoice retrieval, Office approval UX, QR/card providers and guest feedback are cross-stream capabilities, not defects to conceal with UI success. Exact backend stream/contact assignments are not present in the repository; module ownership above must be bound to named owners by the orchestrator.
